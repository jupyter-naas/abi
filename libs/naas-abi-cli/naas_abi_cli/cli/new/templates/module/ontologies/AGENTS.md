# `ontologies/` — AGENTS.md

> Scope: ontology definitions for the `{{module_name_snake}}` module. See the module's [AGENTS.md](../AGENTS.md) for module-wide context.

## What goes here

**RDF / OWL** schemas that describe the vocabulary your module reasons over — classes, properties, axioms — plus the SPARQL that queries them. These TTL files are the single source of truth for the module's domain model.

## Structure

Four folders, each with a distinct job:

```
ontologies/
├── modules/     {{module_name_pascal}}Ontology.ttl        the module's own vocabulary
├── processes/   {{module_name_pascal}}Process.ttl         one BFO process per file
├── queries/     {{module_name_pascal}}SparqlQueries.ttl   templatable SPARQL → agent tools
└── classes/     generated by onto2py — do NOT hand-edit
```

`BaseModule.on_load()` globs `ontologies/**/*.ttl` **recursively**, so all four load with no registration code.

**`modules/`** — the vocabulary the module owns. Answers *what kinds of things exist in this domain?* One ontology per module. Import `abi:Ontology` for the ABI base classes rather than redeclaring `Person`, `Organization` or `Site`.

**`processes/`** — one file per business process, decomposed across the BFO seven buckets. Answers *what happens, and what does it touch?* A process file imports its module ontology, never the reverse: vocabulary must stand alone, while a process is always *about* something.

**`queries/`** — `intentMapping:TemplatableSparqlQuery` individuals. `TemplatableSparqlQueryLoader` turns each into a callable agent tool, so `intentDescription` is a prompt, not a comment: write it as the question a user would actually ask.

**`classes/`** — generated. Thin action-class stubs, one per class, in a directory tree mirroring the ontology IRI (`classes/ontology_demo/{{module_name_snake}}/MyClass.py`). Commit them for IDE completion; never edit them.

## The seven buckets

Every domain class must trace to one of BFO's seven roots. This is **enforced** — `onto2py` refuses to generate from a TTL that violates it. Subclass the matching `abi:` class to inherit the trace:

| Bucket | Question | Subclass | BFO root |
|---|---|---|---|
| WHAT | what is happening | `abi:Process` | `BFO_0000015` |
| WHEN | over what interval | `abi:TemporalRegion` | `BFO_0000008` |
| WHO | which material entity | `abi:MaterialEntity`, `abi:Person` | `BFO_0000040` |
| WHERE | at what place | `abi:Site` | `BFO_0000029` |
| HOW WE KNOW | which record carries it | `abi:GenericallyDependentContinuant` | `BFO_0000031` |
| HOW IT IS | which measurable quality | `abi:Quality` | `BFO_0000019` |
| WHY | which role or disposition | `abi:Role`, `abi:Disposition` | `BFO_0000023` / `BFO_0000016` |

Two validator rules catch most first drafts:

- **`BUCKET_MAPPING`** — a class subclassing nothing traceable to a root. Usually a missing `owl:imports`: the parent lives in a CCO mid-level ontology you did not import.
- **`INHERES_IN`** — a quality, role or disposition with no bearer. Every dependent entity needs an `owl:Restriction` on `bfo:BFO_0000197` (inheres in) or `bfo:BFO_0000196` (bearer of), directly or via a sub-property such as `abi:inheresIn`.

Treat `INHERES_IN` as a modelling check, not a formality. If you cannot name a bearer, the thing is probably not a quality or a role — reconsider the bucket instead of inventing one. A job position that can sit vacant, for instance, is not a role at all: it is a generically dependent continuant, because a BFO role must inhere in a bearer.

## Conventions

- **Stable IRIs** under `http://ontology.naas.ai/{{module_name_snake}}/`. Once published, never repurpose one.
- **One `owl:imports` statement per IRI.** A comma-separated continuation is silently dropped by onto2py's codegen pre-scan, and the classes behind it degrade to bare `URIRef` ranges.
- **Locator annotations** on every ontology header — `abi:pythonPackage`, `abi:ontologyResource`, `abi:pythonResource`. Without them, other modules importing your IRI cannot resolve it to a Python module.
- **Pair every relation with its inverse**, and subclass an `abi:` relation so the BFO semantics carry over.
- **Schema only.** Named individuals belong in pipeline output. Anything in a TTL here lands in the live triple store — example individuals become real query results.
- **English labels and `skos:definition`** on every class and property.

## Regenerating

```bash
uv run python -m naas_abi_core.utils.onto2py {{module_name_snake}}/ontologies/modules/{{module_name_pascal}}Ontology.ttl
uvx ruff check --fix {{module_name_snake}}/ontologies && uvx ruff format {{module_name_snake}}/ontologies
```

One invocation validates the TTL, writes the sibling `.py`, and refreshes `classes/`. The ruff pass is required — generated code is not formatter-clean on first write.

A `could not resolve owl:imports` warning is **not** an error. Pure vocabulary imports (`bfo-core.ttl`, `abi:BFO7Buckets`, the CCO mid-level ontologies) carry no locator annotations, so onto2py skips them by design. The TTL still loads into the triple store in full; only the generated Python loses that cross-file superclass link.

## Using the generated classes

The instance method is `.rdf()`, which returns an `rdflib.Graph`:

```python
from rdflib import URIRef
from {{module_name_snake}}.ontologies.modules.{{module_name_pascal}}Ontology import {{module_name_pascal}}Record

record = {{module_name_pascal}}Record(label="Record 42", record_id="42")
graph = record.rdf()
triple_store.insert(graph, graph_name=URIRef("http://ontology.naas.ai/graph/{{module_name_snake}}"))
```

Import from `ontologies/modules/` (or `ontologies/processes/`) for the model classes; import from `ontologies/classes/` only when you want the action-class stub you have extended.

## Tests

Verify the TTL parses and the expected classes are present:

```python
from pathlib import Path

from rdflib import Graph


def test_ontology_parses():
    g = Graph()
    g.parse(
        Path(__file__).parent / "modules" / "{{module_name_pascal}}Ontology.ttl",
        format="turtle",
    )
    assert len(g) > 0
```

Run:

```bash
uv run pytest {{module_name_snake}}/ontologies
```

## Wiring into the module

1. Declare `TripleStoreService` in `ABIModule.dependencies.services`.
2. `BaseModule.on_load()` auto-discovers and loads every `.ttl` here — no manual `load_schema` calls.
3. Pipelines / workflows that emit triples should target this ontology's classes.
